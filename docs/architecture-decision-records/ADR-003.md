# ADR-003: Dependency-Free Minimal MCP stdio Server

## Status

Accepted. Re-affirmed 2026-08-24 after a fresh online check (latest spec revision still `2026-07-28`; SDK still v2.0.0): the user explicitly chose the hand-rolled server over SDK migration.

## Decision

`simgrep mcp` runs a Model Context Protocol server implemented by hand in `simgrep/mcp_server.py`:
a newline-delimited JSON-RPC 2.0 loop over stdio with support for exactly the methods simgrep
needs — `initialize`, `ping`, `notifications/initialized`, `tools/list`, and `tools/call` —
exposing four tools (`search`, `similar`, `status`, `index`). No MCP SDK and no new runtime
dependency is added.

## Rationale

- **Zero-dependency local-first ethos.** Simgrep's value proposition is a self-contained local
  tool; the protocol subset used here is small, stable, and fully covered by tests.
- **Official SDK v2 evaluated and rejected (researched and re-verified against stable v2.0.0 on 2026-08-24).** The `mcp` Python SDK v2.0.0
  pulls roughly thirteen cross-platform runtime dependencies — pydantic, anyio, starlette, uvicorn, httpx2,
  pyjwt[crypto], opentelemetry-api, sse-starlette, python-multipart, jsonschema, mcp-types, typing-extensions,
  typing-inspection — for a server that only ever speaks stdio. That dependency weight buys transports and
  features simgrep will not use, against the repo's simplicity/performance ethos.
- **Protocol version policy (legacy-era ceiling `2025-11-25`).** Supported versions are
  `2024-11-05`, `2025-03-26`, `2025-06-18`, and `2025-11-25`. A client-requested version from this
  set is echoed back verbatim; anything else falls back to `2025-11-25`.
- **Framing.** One JSON message per line on stdin, one response line per request on stdout.
  Malformed input yields a JSON-RPC error (`-32700`/`-32600`) and the loop continues until EOF;
  the server never crashes on bad input and exits 0 at EOF.
- **Error semantics per SEP-1303.** Tool input-validation failures (missing required fields, wrong
  value types) return normal results with `isError: true` and a human-readable message — they are
  tool execution errors, not protocol errors, so the calling model can self-correct. Only unknown
  tool names and non-object `arguments` are protocol-level `-32602`.
- **No network surface.** Local stdio only — no sockets, no remote endpoints — matching simgrep's
  local-only data posture.
- **Lazy model loading.** The module imports heavy runtime code inside handler bodies, so
  handshake and discovery respond instantly; the embedding model loads only when a tool actually
  needs it.

## Protocol currency: the 2026-07-28 spec revision (evaluated 2026-08-24)

The latest spec revision (`2026-07-28`) is a major rework: it removes the `initialize` handshake
and `ping`, introduces `server/discover`, per-request `_meta` versioning, and a required
`resultType`. Crucially, that revision REQUIRES clients to fall back to the legacy `initialize`
handshake when a server answers their pre-initialize probe with an implementation-defined error —
commonly `-32601`, exactly what this server does for unknown methods. A legacy-era server therefore
remains fully interoperable with modern clients BY SPEC.

This server deliberately stays legacy-era:

- No `server/discover` implementation (answering it would falsely claim modernity).
- No `resultType` field.
- `ping` is kept.

## Revisit trigger

Re-evaluate this decision if either of the following happens: MCP clients start dropping the
mandated legacy-fallback behavior, or the deprecation windows for the legacy handshake close in
client implementations. At that point the hand-rolled loop must be extended deliberately or
reconsidered against the SDK.

## Consequences

- Tool payloads reuse `output.enrich_result`/`format_json`, so MCP results are byte-compatible
  with `simgrep search --format json`.
- stdin anchors (`-`) are unsupported in `similar` because stdin is the protocol channel.
